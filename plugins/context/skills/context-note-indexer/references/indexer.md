# Interpret a note

A note is a durable record, excerpt, observation or summary supplied for this
workspace. It can contain both raw material and an author's interpretation.
Read the source's own labels and actual content before deciding what it proves.
Do not classify it by filename, a keyword like “FAQ”, or the fact it is Markdown.

Separate original wording from commentary when both are present. An exact
excerpt can support what its author wrote within the quoted scope. A paraphrase
supports the supplied account, not a verbatim quotation. A local observation
supports that observed case; it is not automatically a universal rule. A user
correction may invalidate an existing page even when it cannot justify a new
standalone article. Keep useful source boundaries; do not strip raw passages
out of sources to make them look like final knowledge.

For example, a note may contain an error message, a successful recovery command
and “perhaps the default timeout is too short.” The error and successful attempt
can support a bounded troubleshooting entry. The speculation must not become a
default-value claim or a root cause. If current code or a maintained document is
already in authorized scope, check it; otherwise identify what remains unknown.

A second note may correct one sentence in an approved guide. Compare the old
sentence, its source and the new correction. Revise the relevant explanation if
supported; do not create a “knowledge improvement” page that merely announces
the correction. A third note may define a durable term absent from the guide:
that can justify a new reference entry when the reader needs it.

Ask only about missing information that changes a decision: whether an apparent
proposal was adopted, which version a correction applies to, or whether raw text
is actually a quote. Do not demand every possible metadata field. Where the
note itself states the boundary, use it and proceed within authorization.
