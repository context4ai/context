# Context 知识查询

只根据 Context 构建的已批准知识包回答。每个 Context 知识包都带同一份本 Skill，
所以一份就能服务项目里安装的全部知识包：先确定相关的包，再沿索引缩小范围；正文是
事实证据，记忆和 frontmatter 摘要不是。

## 找到知识包

先列出本 Skill 能读取的知识包，再决定去哪里找：

```bash
node <本 Skill 目录>/scripts/search.mjs --list
```

脚本按以下顺序查找并合并结果：

1. 传入的 `--root <包目录>`。
2. 脚本或当前目录所在的知识包。
3. `--base <包集合目录>` 下的全部知识包。
4. 环境变量 `CONTEXT_KNOWLEDGE_PACKAGES` 列出的目录（用平台路径分隔符分隔）。
5. 当前发行版支持的宿主包管理器所记录的知识包。

每一项显示包名、版本、目录以及是否有检索说明。用户点名了某个包或团队时只查它；
否则先读各包的 `index.md` 和检索说明，选出范围与问题相符的包，其余不打开。

## 查询步骤

1. 判断请求属于实体查找、解释、流程、规则、关系、细节还是覆盖检查。
2. 选中的包有 `others/context/search-guide.md` 时先读它：其中列出该包的术语、
   同义词、常见问题和首选入口页。
3. 从最相关的根索引开始，例如 `{{wikisRoot}}/index.md`，再沿链接进入具体页面。
4. 只读取回答所需的章节；frontmatter 用来选择范围，不作为事实依据。
5. 查询关系或影响范围时，读取明确说明；同名、目录位置或链接本身不能证明关系。
6. 结论来自可见章节正文，引用对应的包、页面和章节。多个包都有贡献时分别引用，
   不要合成任何一页都没有写明的结论。
7. 如果知识包里没有证据，明确报告缺口和已经检查的范围，不要根据邻近内容推断。

| 根目录 | 用途 |
|---|---|
| `{{wikisRoot}}/` | 代码、业务和产品说明。 |
| `{{guidesRoot}}/` | 架构、流程、FAQ、决策、故障和排障说明。 |
| `{{rulesRoot}}/` | 标准、约束、验收条件和测试场景。 |
| `{{featsRoot}}/` | 被选择进入包内的功能知识。 |

缺少某个根目录表示该知识包没有选择这一类别。

若存在 `{{wikisRoot}}/imports.md`，它只列出外部入口，不代表内容已随包分发或已安装；
`{{wikisRoot}}/repo-content.md` 是生成的仓库入口页，不是批准知识文章。仅在相关且
有权访问时沿链接读取；不能因列出了 Skill 或插件就安装或执行。

## 检索

索引和页面结构无法确定范围，或候选页面太大时才检索。

- 使用检索说明里的业务词、代码符号和同义词；多跑几条互补的查询，而不是一条很长的。
- 没有结果时换成等价词或上位词；结果太多时按包、根目录或更具体的符号收窄。
  一次没搜到不能证明不存在。
- 精确名称、API、配置键、路径或错误信息用 `rg`。
- 多个词、中文短语或跨多个包时运行随附的 BM25 排序脚本：

```bash
node <本 Skill 目录>/scripts/search.mjs --query '<检索词>' --limit 8
node <本 Skill 目录>/scripts/search.mjs --query '<检索词>' --package <包名>
```

不带 `--package` 时在所有找到的包中统一排序。脚本按标题和有限行区间机械切块，返回
包、路径、行区间、标题和预览，不理解语义。每个命中都只是线索，回答前要打开对应页面和章节。

## 回到原始来源

每篇发布的页面末尾都有从工作区出处导出的 `Sources` 一节。只有包内正文不足以回答，
或答案依赖代码当前行为时，才去读原文：

| 出处 | 怎么读 |
|---|---|
| 带提交和行区间的代码仓库链接 | 用宿主已授权的方式在该提交读取：已配置的只读代码检索服务，或稀疏浅克隆到 `.tmp/context-knowledge-query/<host>/<repository>/<commit>/`。不要把更新后的分支头当作被引用的版本。 |
| 文档链接 | 打开的是当前文档；行区间对应写作时采集的副本。现文不同时如实说明。 |
| 没有链接的条目 | 原文无法从包里访问，只依据包内正文并说明这一点。 |

原文与包内正文分开引用。原文读不到时保留包内结论，说明哪些没能核对，然后继续。
不要修改项目文件；用完删除临时克隆。

## 证据约定

| 证据 | 用途 |
|---|---|
| 包与页面路径 | 身份与引用句柄。 |
| frontmatter 标题、描述和标签 | 仅用于导航和选择范围。 |
| Markdown 标题 | 定位并引用页面内的章节。 |
| 可见章节正文 | 事实结论的主要依据。 |
| `Sources` 条目及据此读到的原文 | 包外的补充依据，单独引用。 |
| 根索引与 `context-build-inventory.json` | 包的范围与覆盖情况。 |

不要根据页面共现推断关系。发布页面不需要生产标识或出处记账即可使用；引用可读路径和
标题即可。只有覆盖问题或维护者需要 `dist_path` → `approved_path` 时才打开
`context-build-inventory.json`。

## 引用与缺口

```text
页面：  <结论> [<包>: <root>/path/page.md]
章节：  <结论> [<包>: <root>/path/page.md, 标题: <可见标题>]
关系：  <结论> [<包>: <root>/path/page.md, 标题: <支撑说明>]
原文：  <结论> [<仓库>@<提交>: <路径> L<起>-L<止>]
覆盖：  <结论> [<包>: context-build-inventory.json]
```

缺少证据时返回：

```text
缺口：可用知识包中没有 <缺失点> 的证据。
已检查：<包、索引、页面或原文>。
下一步可查：<已知的来源文档或页面>。
```

区分“这些知识包没有证据”和“这件事不成立”。不要用记忆、以往对话或未读过的文件填补缺口。

## 最终总结中的网站链接

根据实际读过的页面回答后，可以附上相关文档链接。从包目录读取 `context-site-map.json`，
或读取 `others/context/context-site-map.json`。把读过的页面与 `pages[].package_path` 或
`approved_path` 匹配，使用其 `title`，并把 `site_path` 相对于 `site_url` 解析；
`site_url` 已包含部署基础路径。只引用匹配的文章，去重，不要编造章节锚点。

这是本地格式化步骤，不是检索或验证。不要为了加链接去探测 URL、打开浏览器或检查远端
版本。映射、URL 或匹配页面缺失或格式错误时，保留本地引用并继续。
